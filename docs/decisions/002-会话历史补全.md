# ADR-002: 会话历史补全与上下文压缩

## 状态

Accepted（2026-06-03）

## 背景

当 Higo 配置记忆引擎（higo2ov）后，Higo 的 `buildModelMessagesForTurn()` 方法会从 transform 请求中丢弃历史会话消息。引擎只收到 `[system, contextEnv, currentUser]`，导致 LLM 在同一会话中遗忘之前的对话内容。

Higo 原有的两种上下文压缩机制（被动截断和主动摘要）在配置记忆引擎后均失效：
- `buildMessages()` 历史选取分支被跳过
- `memory_summarize_to_section` 工具因无历史可摘要而无法触发

由于 Higo 代码不能被修改，higo2ov 必须自行实现历史补全和上下文压缩。

## 决策

在 transform 响应中，将 OpenViking session context 中的归档摘要和活跃消息组装为 `<session-history>` 区块，与 `<relevant-memories>` 一起注入到对话中，并基于 token 预算做截断。

## 方案详情

### 数据源

`get_session_context()` 返回：
- `latest_archive_overview`：最近一次 commit 的摘要
- `pre_archive_abstracts`：更早的 commit 摘要列表（旧→新排序）
- `messages`：尚未 commit 的活跃消息
- `estimatedTokens`：活跃消息的估算 token 数

### Memory Text 结构

```
<session-history>
  [pre_archive_abstracts[0]]
  [pre_archive_abstracts[1]]
  ...
  [latest_archive_overview]
  - user: ...
  - assistant: ...
</session-history>

<relevant-memories>
  - [profile] ...
  - [event] ...
</relevant-memories>
```

### Token 预算分配

```
total_budget = modelContextWindowTokens * 0.85
fixed_costs = system + contextEnv + currentUser + overhead
history_budget = total_budget - fixed_costs
```

`history_budget` 全部分配给 `<session-history>` 区块。`<relevant-memories>` 继续使用 `recall_token_budget`（默认 2048），与历史预算解耦。

### 截断策略

从旧到新遍历，累加 token 数，超预算停止：
1. 最旧的 `pre_archive_abstracts` 先丢
2. 然后是旧的活跃 `messages`
3. `latest_archive_overview` 和最新的消息始终保留

### 消息格式化

- 活跃消息：`- {role}: {text}`，单条截断到 500 字符
- 归档摘要：`[归档摘要]\n{overview_text}`，截断到 800 字符
- 排除当前轮次最后一条消息（避免与 Higo 的 currentUser 重复）

## 与 OV Commit 机制的协作

- **OV commit** = 主动压缩（异步、LLM 生成摘要、质量高）
- **higo2ov 截断** = 被动压缩（同步、基于 token 预算、保留近期精确消息）

两者互补：commit 前注入完整活跃消息，commit 后摘要 + 新活跃消息，多次 commit 后 pre_archive_abstracts 确保历史不丢失。

## 后果

### Pros

- LLM 在同一会话中能看到之前的对话内容
- 截断策略与 Higo 原有行为一致（保留最新上下文）
- 利用 OV 现有 commit 机制，无需额外开发

### Cons

- token 估算使用 `len(content) // 4`，不够精确（没有 tiktoken 可用时）
- `history_budget` 和 `recall_token_budget` 分离，整体预算可能超支
- 活跃消息过多时，`<session-history>` 可能占满全部 budget，挤压 `<relevant-memories>`
