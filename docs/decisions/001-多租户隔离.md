# ADR-001: 多租户数据隔离——OpenViking 按用户独立 Account

## 状态

Accepted（2026-06-02）

## 背景

此前方案将 Higo 的 `userId` 透传到 OpenViking 的 `X-OpenViking-User`，但仍共用同一个 `default` account 和 ROOT key。这导致：

1. **Session 数据在 account 内全局可见**（OpenViking 的 `viking://session/{id}` 是 account-global 的）
2. **权限边界模糊**：所有请求都用 ROOT key，一旦 higo2ov 被攻破，全量数据暴露
3. **无法级联清理**：OpenViking 的 `delete_account` 可以清理 account 下全部数据，但幽灵 account（未在 manager 注册）无法被清理

## 决策

将方案升级为**每个 Higo 用户在 OpenViking 中拥有独立的 account + USER key**。

## 方案详情

### 目标

1. 每个 Higo 用户对应一个 OpenViking account，session、user memories、resources 完全物理隔离
2. higo2ov 自动懒创建 account 和 USER key，无需人工维护账户映射表
3. 业务请求使用 USER key（非 ROOT key），权限最小化
4. 映射关系持久化到本地 registry，重启后可恢复

### OpenViking 关键机制

- **Account 生命周期 API**：`POST /api/v1/admin/accounts` 创建，`POST /api/v1/admin/accounts/{id}/users` 注册 user 返回 USER key
- **USER key 格式**：`account_id.user_id.secret`（base64url），自带 account 和 user 信息
- **物理路径隔离**：`viking://` URI 在存储层按 account_id 分目录
- **ROOT key 权限**：可覆盖 account_id 和 user_id，但 tenant-scoped API 必须显式提供 header

### 架构

```
Higo 请求
    │
    ▼
┌─────────────────────────────────────┐
│  main.py                              │
│  - 提取 session.userId                │
│  - 格式化为 higo_{userId}             │
└─────────────┬───────────────────────┘
              │
              ▼
┌─────────────────────────────────────┐
│  AccountRegistry                      │
│  - 内存缓存（dict）                    │
│  - 本地持久化（JSON + atomic write）   │
│  - 懒创建逻辑（asyncio.Lock）          │
└─────────────┬───────────────────────┘
              │
    ┌─────────┴──────────┐
    │                      │
    ▼                      ▼
┌──────────┐      ┌──────────────┐
│ AdminClient │      │ UserClient     │
│ (ROOT key)  │      │ (USER key)     │
│ 只用于 admin │      │ 用于业务 API   │
└─────┬─────┘      └──────┬───────┘
      │                    │
      ▼                    ▼
   OV admin API         OV data API
   /api/v1/admin/...   /api/v1/sessions/...
```

### 核心模块

**AccountRegistry**：管理 `higo_user_id -> {account_id, user_id, api_key}` 映射
- 内存缓存（`self._cache`）
- JSON 文件持久化（atomic write）
- 懒创建：asyncio.Lock + 双重检查
- 409 Conflict 时降级 regenerate key

### 请求流程

**Transform 请求**：
1. `main.py` 提取 `userId`，格式化为 `higo_{userId}`
2. `account_registry.get_client("higo_xxx")`
3. 查缓存 → 查 registry → 懒创建（admin API）→ 返回 USER client
4. USER client 调用 OV 业务 API

### 风险与对策

| 风险 | 对策 |
|------|------|
| 并发创建 | asyncio.Lock 保护懒创建逻辑，内部双重检查 |
| Registry 丢失 | 懒创建时捕获 AlreadyExistsError，然后 list users + regenerate_key |
| Account ID 格式 | Higo userId 是 UUID，加 `higo_` 前缀后符合 OV validate_account_id |
| 性能 | 内存缓存，只有首次创建有开销 |
| OV 不可达 | 抛异常，Higo 侧按无记忆处理 |
| 向后兼容 | 不带 userId 的请求 fallback 到 admin_client |

## 后果

### Pros

- 每个用户数据物理隔离，安全边界清晰
- USER key 权限最小化，即使泄露也只影响单个用户
- 支持级联清理（delete_account）
- 向后兼容：不带 userId 的请求仍走 ROOT key

### Cons

- 首次请求新用户时有 admin API 调用开销（约 100-300ms）
- 需要维护 `.account_registry.json` 文件
- ROOT key 仍保存在 higo2ov 服务器，存在泄露风险
